# モデル仕様

このシステムがどういう理屈で「エントリーすべき日」を決めているかの説明。
係数を触る前にここを読むこと。

---

## 1. 全体の考え方

判断の単位は **「ボーナスストアPlusに参加した場合」と「しなかった場合」の差分** 。

```
純増効果 = 増分GMV × 粗利率 − 増分ポイント原資 + 新規客のLTV
```

ここで最も間違えやすいのが **どの付与が自社負担でどれがモール負担か** 。

販促カレンダーには毎日7%から14%までの付与率が並んでいるが、そのほとんどは
モール負担であって自社のコストにはならない。全部を自社原資として計上すると、
原資が数倍に膨らんだ非現実的な提案になる。

```
顧客が受け取る総付与率  = モール負担 + 自社負担     ← 需要のドライバー
自社ポイント原資        = 自社負担ぶんのみ × GMV    ← コスト
```

2026年10月のカレンダーでは、自社負担は **ストアポイント1% ＋ ボーナスストアPlusの
自社設定率** だけ。残りはすべてモール負担。

> この資金負担区分は `funding: mall | store` でスケジュールYAMLに持たせている。
> 実際の請求条件が違っていれば、YAMLの書き換えだけで切り替えられる。

## 2. 需要モデル

```
セッション(d) = base_sessions × 曜日 × 給料日 × 月次季節
                × 市場規模係数(全ストア共通の付与率)
                × 集客係数(付与率とは別の広告効果)
転換率(d)     = base_cvr × シェア係数(自社だけの上乗せ)
注文数(d)     = セッション(d) × 転換率(d)
```

### 2.0 集客と転換率を分ける理由

実績ではこの2つが別々に動いている。

| | 2025-09 | 2026-08 | 変化 |
|---|---:|---:|---|
| セッション | 6,909 | 7,988 | +16% |
| 転換率 | 8.4% | 10.3% | **+23%** |
| 平均注文単価 | 4,526円 | 5,578円 | +23% |

成長の大半は集客ではなく転換率と単価の改善による。注文数1本で持つと
この構造が潰れ、前方予測を誤る。分けておけば市場規模係数はセッションに、
シェア係数は転換率にかかり、**どちらも実績で検証できる量に対応づく**。

### 2.1 市場規模とシェアを分ける理由

販促カレンダーの施策は2種類ある。この違いが提案の質を決める。

| 種類 | 例 | 効果 |
|---|---|---|
| **全ストア対象** | 5のつく日、ファーストデイ、定常施策 | 競合も同条件。自社シェアは動かず、**モール全体の来訪者数**が増える |
| **参加資格つき** | ボーナスストアPlus参加、プロモーションパッケージ加入 | 持っていない競合に対する**優位**。自社シェアが動く |

この2つを1本の反応関数にまとめると失敗する。「すでに付与率が高い日は追加の効きが
鈍い」という逓減が効きすぎて、**モールが最も集客している5のつく日を避ける**
提案になる。実務感覚と逆で、これはモデルの作りに起因する歪みである。

分けておけば、5のつく日は「パイが大きい日」として、ボーナスストアPlus指定日は
「自社だけ有利になれる日」として、それぞれ正しく評価される。

### 2.2 市場規模係数

```
市場規模係数 = (全ストア共通の付与率 / baseline_rate) ^ market_elasticity
```

`baseline_rate` は定常施策だけの日の付与率（2026年10月なら7%）。そこで1.0になる。

`market_elasticity` の既定 0.9 は「5のつく日（7%→11%）で来訪が約1.5倍」に
合わせた値。**自社の実績で5のつく日の伸びが分かれば、そこから逆算して設定し直すこと。**

### 2.3 シェア係数

```
優位 = 参加資格つき施策で開く分 + 自社設定率
シェア係数 = 1 + share_gain_at_reference × (優位 / reference_advantage) ^ share_elasticity
```

**比率ではなく絶対差で見るのが要点。** 顧客にとって上乗せ2ポイント分の価値は、
その日の基準率が7%でも11%でも同じ金額（2万円の注文なら400円）。比率で見ると
基準率が高い日ほど同じ上乗せが小さく評価され、2.1で述べた歪みが出る。

既定値の意味は「競合に対して2ポイントの優位があるとき、注文が20%増える」。
優位を増やすと `share_elasticity` で逓減する。

| 優位 | シェア係数 |
|---:|---:|
| +1pt | 1.123 |
| +2pt | 1.200 |
| +4pt | 1.325 |
| +6pt | 1.425 |

### 2.4 エントリー判断との関係

ボーナスストアPlusに参加すると、その日だけ開くモール負担の上乗せがシェア側に乗る。
**参加しなければその分がまるごと機会損失になる。**

2026年10月では、参加でモール負担の上乗せが開くのは **10/2・7・16・20・27・28 の
6日だけ**。他の日は参加しても自社のポイントを配るだけになる。

## 3. 注文下限金額と付与上限

犬猫用家電のような高単価商材では、この2つが逆方向に効く。

| 条件 | 効き方 |
|---|---|
| 注文下限金額 | 下限未満の注文には付かない → **低単価側**で効果が消える |
| 付与上限 | 1注文あたりの上限で頭打ち → **高単価側**で効果が消える |

平均単価だけで判断するとどちらも見落とす。**分布で積分する必要がある。**

### 実測分布を優先する

このストアの注文単価は **ユニーク価格が350種しかなく、上位10価格で全体の56%**
を占める。最頻価格1,780円だけで19%。SKU価格に張り付いた離散分布で、
連続分布の近似が成り立たない。

| 注文下限 | 実測 | 対数正規(σ=0.55) | 誤差 |
|---:|---:|---:|---:|
| 3,000円 | **48.4%** | 79.9% | +31.5pt |
| 5,000円 | **30.8%** | 47.8% | +17.0pt |

対数正規で近似するとボーナスストアPlusの価値を1割ほど水増ししてしまう。
そのため注文明細があれば実測分布をそのまま使う（`distribution.py`）。
ソート済み配列と累積和を持ち、`bisect` で区間和を O(log n) で求める。

明細が無いときは対数正規で近似する:
`V ~ LogNormal(μ, σ)`（`E[V] = aov`）

```
期待付与率 = E[ min(V·r, cap) · 1{V ≥ min_order} ] / E[V]

            = ( r · E[V ; min_order ≤ V ≤ cap/r] + cap · P(V > cap/r) ) / E[V]

  E[V ; a ≤ V ≤ b] = aov · ( Φ(z(b)) − Φ(z(a)) ),  z(x) = (ln x − μ − σ²) / σ
  P(V > x)         = 1 − Φ( (ln x − μ) / σ )
```

### 実測分布での効き方

明細7,543件から算出した実効付与率。

| 施策 | 表示 | 注文下限 | 該当率 | 実効率 |
|---|---:|---:|---:|---:|
| 5のつく日・感謝デー | 4% | なし | 100% | 4.00% |
| ファーストデイ | 3% | 3,000円 | **48%** | 2.44% |
| ポイントアップ | 4% | 3,000円 | **48%** | 3.25% |
| ボーナスストアPlus | 2% | 3,000円 | **48%** | **1.62%** |
| プレミアムな日曜日 | 5% | 5,000円 | **31%** | 3.31% |
| 爆買WEEK(4%/7%段) | 4%/7% | 合計5,000円 | 31% | 2.81% |
| **モールクーポン** | 1,000円 | 25,000円 | **0.5%** | **0.11%** |

**モールクーポンは実質的に機能しない。** 爆買WEEKの7%段（合計20,000円以上）も
該当率1%で、ほぼ4%段のみが効く。
逆に1注文あたり付与上限5,000円はこの単価では完全に非拘束（5%でも254円）。

### 段階付与は注文ごとに段を判定する

買い回り型（爆買WEEK）は、平均単価で段を決めて全注文に適用してはいけない。
平均5,076円で4%段と判定すると、最下段5,000円に届かない1,780円の注文にも
4%を掛けることになり、実効率を4.00%と過大評価する（正しくは2.81%）。

注文ごとにその金額で段を判定し、段ごとの区間で積分する。
買い回りは複数注文の合計で段が決まるため、1注文だけで判定する分
**保守的な見積り**になる。

## 4. コストは限界差分で見る

ストアポイント1%は参加しようがしまいが毎日かかる。したがって
エントリー判断で増えるのは差分だけ。

```
増分原資 = 参加時の原資 − 不参加時の原資
        = (参加時の注文 × 単価 × 自社実効率) − (不参加時の注文 × 単価 × 常時の自社率)
```

注意すべきは、参加時の原資が **増分注文だけでなく全注文にかかる** こと。
エントリーしなくても発生したはずの注文にもポイントは付く（カニバリ）。
これを差し引かないとどの日も黒字に見える。

## 5. 損益分岐

粗利率 `m`、自社実効還元率 `e` のとき、元が取れる注文増加率 `u` は

```
(1+u)·m − (1+u)·e = m   →   u = e / (m − e)
```

`e ≥ m`（実効還元率が粗利率以上）なら **どれだけ売れても赤字**。

## 6. 最適化

月次のポイント原資予算の下で、各エントリー単位につき
「見送る」か「参加して還元率をひとつ選ぶ」の択一を決める。
**multiple-choice knapsack** として動的計画法で解く。

貪欲法（費用対効果の高い順に取る）では
「安い日を2つ取るより高い日を1つ取る方が良い」ケースを取りこぼすため使わない。

### 目的関数

| `--objective` | 内容 |
|---|---|
| `gmv`（既定） | 利益床つきの売上最大化。ROAS下限と純増効果の下限を満たす範囲で増分GMVを最大化 |
| `profit` | 純増効果の最大化 |

### エントリー単位

| 種類 | 単位 |
|---|---|
| 通常の日 | 1日 = 1単位 |
| 期間一括エントリー（爆買WEEKなど） | 期間全体で1単位（all-or-nothing） |

爆買WEEKのように月を跨ぐ施策は `extends_to` で計画対象を延長して扱う。

### 制約

- `min_roas` / `min_net_value`: 自社の採算ライン
- `entry_deadline`: 締切を過ぎた単位は選択不可（機会損失として別掲）
- `mandatory_benefit_ids`: 採算に関わらず確保する（残予算で他を最適化）

## 7. 校正できるもの・できないもの

入力の粒度で決まる。**できないものは仮値のまま残し、レポートに明記する。**

| 係数 | 月次実績 | 日次実績 | 日次＋エントリー記録 |
|---|:---:|:---:|:---:|
| `base_sessions` | ○ | ○ | ○ |
| `base_cvr` | ○（セッション列が必要） | ○ | ○ |
| 月次季節係数 | △ | ○ | ○ |
| `aov` | ○ | ○ | ○ |
| 曜日係数 | × | ○ | ○ |
| 給料日サイクル係数 | × | ○ | ○ |
| `market_elasticity` | × | × | ○ |
| `share_gain_at_reference` | × | × | ○ |
| 注文単価の分布 | × | × | **注文明細があれば実測（完了）** |

△ = 1ヶ月あたり観測1点のため弱い推定。

### 月次校正の手順

```
1. カレンダー構成の除去
   weight(m) = Σ_{d∈m} 曜日係数(d) × 給料日サイクル係数(d)
   日次水準(m) = セッション(m) / weight(m)     ← セッション列がなければ注文数
2. トレンド除去 — log(日次水準) に Theil–Sen 推定（ペア傾きの中央値、外れ値に強い）
3. 季節係数 — 残差を 1.0 方向へ縮小
   month_factor = 1 + λ × (残差 − 1)      λ = 0.5（既定）
4. 平均1に正規化し、スケールを base_sessions に吸収
5. 販促イベントの上振れを差し引く（下記）
6. 転換率は別系列として Theil–Sen でトレンドを取り、base_cvr にする
   （季節性はセッション側に寄せ、CVRはトレンドのみ）
7. aov は直近3ヶ月の 売上/注文数 の中央値
```

### 二重計上の補正（2系統ある）

月次の実績には、その月の販促イベントによる上振れが **すでに含まれている**。
一方モデルは係数を掛けてその上振れを作る。補正しないと二度乗せることになり、
ベースライン予測が系統的に過大になる。

補正は**集客側と転換率側の2系統**が必要。

| 実績の量 | 押し上げていた施策 | 割る係数 |
|---|---|---|
| セッション | 全ストア対象（5のつく日など） | 市場規模係数の平均 |
| 転換率 | 参加資格つき施策＋**自社のボーナスストアPlus参加** | シェア係数（月ごと） |

`calibrate --schedule --participation` を指定すると両方が適用される。
**`--schedule` を省略するとどちらも効かず、予測が過大になる。**

### 転換率側は月ごとに補正する

自社の参加は途中の月から始まっていることがある。その場合、
トレンドを当ててから定数で割ると、参加による段差をトレンドとして
吸収してしまう。**月ごとに補正してからトレンドを当てる**。

```
adjusted_cvr(月) = observed_cvr(月) / share_factor(月)
base_cvr = Theil–Sen(adjusted_cvr) の直近月の値
```

過去の販促カレンダーは残っていないため、**各月も対象月と同じ販促構成だった**
と仮定する。また販促日と自社の参加日の重なり方は分からないため、
**両者を独立**と見なして掛け合わせる。

実データでの補正係数は 1.063（非参加月）〜1.180（参加月）。

### 縮小推定を使う理由

13ヶ月のデータでは1ヶ月あたり観測が1点しかない。素の残差をそのまま季節係数に
すると、その月固有の販促やノイズを「季節性」として焼き込んでしまう。
λ=0.5 で 1.0 方向へ引き戻すことで、過学習を抑える。

## 8. シェア反応は実測できるか

エントリーの価値は「自社の付与率の優位がどれだけ注文を増やすか」
（`share_gain_at_reference`）で決まる。参加履歴があれば実測できるはずだが、
実データでは **できなかった**。

```
log(CVR) = a + b·t + c·参加率

  トレンド（参加率なし） +2.75%/月
  トレンド（参加率あり） +2.46%/月
  参加率の係数 +0.100（SE 0.220, t=0.46）
  参加率と時期の相関 0.827
```

参加開始が成長トレンドの立ち上がりと重なっており、
「参加したから伸びた」のか「もともと伸びていた」のかを分離できない。
非参加6ヶ月の平均CVR 8.73% → 参加7ヶ月 10.52%（+20.5%）という差も、
**トレンド単独（+2.75%/月 × 6.5ヶ月 = +19.4%）でほぼ説明がつく**。

`participation.estimate_share_response` は、次のいずれかに当てはまると
`identifiable=False` を返す。

- 参加率と時期の相関が 0.75 を超える
- 参加率の係数の t値 が 2 未満

**これを解くには日別の注文数・セッション数が要る。**
参加日と非参加日を直接比較できるため、トレンドの影響を受けない。

## 9. このモデルが扱っていないこと

正直に書いておく。運用で補う必要がある。

- **在庫制約**: 売れすぎて欠品する可能性を見ていない
- **競合の出方**: 同カテゴリの他店が同日に高還元を打つと効果は下がる。
  シェアモデルの基準は「参加資格つき施策を何も持たないストア」で固定している
- **広告との相互作用**: 同日に広告を増やした効果と分離できていない
- **需要の先食い**: イベント日の売上が翌週分を前借りしている分を戻していない
- **祝日**: 祝日補正を持っていない（月次係数に吸収される）
- **商品単位の差**: 本体と消耗品で反応が違うが、店舗単位で平均している
- **くじ・抽選型の施策**: 当選確率が非公開で期待値を置けないため、
  需要モデルに入れず注記として扱っている
- **ユーザー側の月次・期間上限**: 1注文あたりに引き直して評価しているため、
  同一顧客が月内に何度も買う場合は効果をやや過大に見積もる
