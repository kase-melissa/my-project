# モデル仕様

このシステムがどういう理屈で「エントリーすべき日」を決めているかの説明。
係数を触る前にここを読むこと。

---

## 1. 全体の考え方

判断の単位は **「エントリーした場合」と「しなかった場合」の差分** 。

```
純増効果 = 増分GMV × 粗利率 − ポイント原資 + 新規客のLTV
```

ここで最も間違えやすいのが **ポイント原資は増分GMVではなく全GMVにかかる** こと。
エントリーしなくても発生したはずの注文にもポイントは付く。この自然発生分への
コスト（カニバリ）を差し引かないと、どの日も黒字に見えてしまう。

```
ポイント原資 = エントリー時の全注文 × 注文単価 × 実効還元率
                ~~~~~~~~~~~~~~~~~~~~
                増分だけではない
```

---

## 2. 需要モデル

日次の注文数を乗算モデルで表す。

```
注文数(d) = base_orders
          × 曜日係数(d)
          × 給料日サイクル係数(d)
          × 月次季節係数(d)
          × イベント需要倍率(d)          ← エントリー非依存
          × (1 + エントリー上乗せ率(d, r)) ← エントリーして初めて得られる
```

### 2.1 traffic_multiplier と entry_uplift を分ける理由

この分離がシステムの中核。

| 項目 | 意味 | エントリーしないと |
|---|---|---|
| `traffic_multiplier` | イベント告知によるモール全体の集客増。自社商品にも流入する | **得られる** |
| `entry_uplift` | 特集面掲載＋「ボーナスストア対象」絞り込み検索での露出＋還元率表示によるCVR改善 | **まるごと失う** |

「プレミアムな日曜日」「Yahoo!ショッピング感謝デー」「超PayPay祭」「爆買いWEEK」は
いずれもエントリーが参加条件なので、エントリーしなければ `entry_uplift` 分がそのまま
機会損失になる。**この機会損失の大きさがそのまま提案の優先順位**になる。

だからスケジュール登録時に `entry_required: true` かつ `entry_uplift: 0` は
設定ミスとして弾いている（エントリーの価値が0と評価されてしまうため）。

### 2.2 イベント重複日の扱い

10/25 のように「日曜 × 5のつく日 × 超PayPay祭グランドフィナーレ」が重なる日は、
倍率を単純に掛け合わせない。同じ「購買意欲の高い顧客層」を取り合うため、
実際には掛け算にならないからである。

効果を大きい順に並べ、2件目以降を `overlap_decay^i` で割り引いて合算する。

```
合成効果 = Σ_i  効果_i × decay^i     (効果は降順)
```

例）+55%, +42%, +40% が重なる日（decay=0.55）:
- 単純積: 1.55 × 1.42 × 1.40 = 3.08倍
- 本モデル: 1 + 0.55 + 0.42×0.55 + 0.40×0.30 = **1.90倍**

### 2.3 暦要因

公式スケジュールに載らないが毎月効く要因。

| 要因 | 根拠 |
|---|---|
| 曜日 | 日曜が最も強く、火〜水が弱い |
| 給料日サイクル | 25日以降と月初に高単価家電の決済が寄る |
| 5のつく日 | PayPay還元が積み上がりモール全体の需要が跳ねる |
| ゾロ目の日(11/22) | クーポン施策が当たりやすい |
| 月次季節性 | ペット家電は換毛期(春・秋)と猛暑期、年末商戦に動く |

**二重計上の防止**: 公式スケジュールに明記のある日は、暗黙の暦イベント
(5のつく日・ゾロ目)を適用しない。常に公式スケジュールを正とする。

---

## 3. 還元率への反応

還元率を2倍にしても効果は2倍にならない。逓減する。

```
反応(r) = (体感還元率 / reference_rate) ^ rate_elasticity      (指数 < 1)
エントリー上乗せ率 = 合成entry_uplift × 反応(r)
```

**体感還元率** は表示還元率そのものではなく、1注文あたりポイント上限で
頭打ちになった後の率を使う。

```
体感還元率 = min(表示還元率, 上限ポイント / 注文単価)
```

高単価商材ではここが効く。単価5万円・上限5,000円なら、表示を10%にしても
顧客が受け取るのは10%ではない。**還元率を上げても顧客の体感メリットが
増えない領域に入る**ため、上げ幅に見合った効果が出ない。

---

## 4. ポイント原資（実効還元率）

注文単価を対数正規分布 `V ~ LogNormal(μ, σ)` （`E[V] = aov`）で近似し、
1注文あたり上限 `cap` を考慮した実効還元率を閉形式で求める。

```
実効還元率 = E[min(V·r, cap)] / E[V]

E[min(V·r, cap)] = r·aov·Φ(z₁) + cap·(1 − Φ(z₂))

  t  = cap / r
  z₁ = (ln t − μ − σ²) / σ
  z₂ = (ln t − μ) / σ
```

- 上限に届かない領域では 実効還元率 = 表示還元率
- 高単価側では 実効還元率 < 表示還元率（＝原資が想定より安く済む）

**注意**: 原資が安く済むことは良いことだが、同時に顧客の体感メリットも
頭打ちになっている。片方だけを見ないよう、コスト側（実効還元率）と
効果側（体感還元率）の両方に上限を反映させている。

---

## 5. 損益分岐

粗利率 `m`、実効還元率 `e` のとき、元が取れる注文増加率 `u` は

```
(1+u)·m − (1+u)·e = m   →   u = e / (m − e)
```

`e ≥ m`（実効還元率が粗利率以上）なら **どれだけ売れても赤字** になる。
レポートの「損益分岐の目安」はこの式で計算している（LTVは保守的に除外）。

---

## 6. 最適化

月次のポイント原資予算の下で、純増効果の合計を最大化する。

各エントリー単位について「見送る」か「還元率をひとつ選ぶ」の択一なので、
**multiple-choice knapsack** として動的計画法で解く。

貪欲法（費用対効果の高い順に取る）では
「安い日を2つ取るより高い日を1つ取る方が良い」ケースを取りこぼすため使わない。

### エントリー単位

| 種類 | 単位 |
|---|---|
| 日単位イベント・平常日 | 1日 = 1単位 |
| 期間一括エントリー（超PayPay祭・爆買いWEEKなど） | 期間全体で1単位（all-or-nothing） |

期間が重なる一括エントリーは1つの単位に統合する。
期間内は同一還元率が前提なので、選べる還元率は期間内の積集合を取る。

### 制約

- `min_bonus_rate`: イベント参加に必要な最低還元率
- `allowed_rates`: イベントが許容する還元率の候補
- `min_roas` / `min_net_value`: 自社の採算ライン
- `entry_deadline`: 締切を過ぎた単位は選択不可（機会損失として別掲）
- `mandatory_event_ids`: 採算に関わらず確保する（残予算で他を最適化）

---

## 7. このモデルが扱っていないこと

正直に書いておく。運用で補う必要がある。

- **在庫制約**: 売れすぎて欠品する可能性を見ていない
- **競合の出方**: 同カテゴリの他店が同日に高還元を打つと効果は下がる
- **広告との相互作用**: 同日に広告を増やした効果と分離できていない
- **需要の先食い**: イベント日の売上が翌週分を前借りしている分を戻していない
  （`base_orders` を実績から校正していれば、ある程度は平均的に織り込まれる）
- **商品単位の差**: 本体と消耗品で反応が違うが、店舗単位で平均している
