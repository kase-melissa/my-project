# 月次運用手順

毎月これをなぞれば回る、という手順書。

---

## 月次サイクル

```
前月中旬      販促スケジュールを受領 → YAMLに書き写す
   ↓
前月中旬      check で締切と参加資格を確認
   ↓
前月中旬      plan でエントリー日程を提案させる
   ↓
前月下旬      提案をレビューして確定 → ストアクリエイターProでエントリー
   ↓
翌月初        実績を追記 → calibrate でモデルを校正
```

---

## 手順1: 販促スケジュールを書き写す

受領した該当月の販促カレンダーを `data/promo_schedule/YYYY-MM.yaml` に書く。
`data/promo_schedule/2026-10.yaml` を雛形としてコピーするのが早い。

施策ごとに書く項目:

| 項目 | 内容 |
|---|---|
| `days` / `period` | 開催日。`all`（毎日）／`[5, 15, 25]`（日付）／`period: [開始, 終了]` |
| `rate` | 付与率。買い回り型は `tiers` を使う |
| `coupon_yen` | 定額クーポン（モールクーポンなど） |
| `funding` | `mall`（モール負担）か `store`（自社負担） |
| `eligibility` | 下表を参照 |
| `min_order_yen` | 注文下限金額 |
| `user_cap_yen` / `user_cap_period` | ユーザー側の付与上限と期間 |
| `entry_unit` | `day` か `period`（期間一括エントリー） |

### eligibility の選び方

| 値 | カレンダーの「対象ストア」欄 |
|---|---|
| `all` | 全ストア |
| `promo_package` | プロモーションパッケージ加入ストア |
| `bonus_store_plus` | ボーナスストアPlus参加ストア |
| `bonus_store_plus_excellent` | ボーナスストアPlus参加ストアかつ優良ストア |

**ここを間違えると提案が根本から変わる。** `all` にすべき施策を
`bonus_store_plus` にすると、エントリーしないと得られないものと誤認され、
不要な日にエントリーする提案になる。

### 転記後の検算

カレンダー最下段の「最大付与率」行と突き合わせること。
`tests/test_schedule_2026_10.py` がその検算をしている。新しい月を追加したら
同じ形のテストを書いておくと、転記ミスがそこで止まる。

### 月を跨ぐ施策

爆買WEEKのように翌月まで続く施策は、トップレベルに `extends_to: "2026-11-01"`
を書いて計画対象を延長する。書かないと「対象期間外の日付」としてエラーになる。

### 数値化できない施策

くじのように当選確率が非公開で期待値を置けないものは `benefits` に入れず、
`notes` に書く。レポートに注意事項として出る。

---

## 手順2: 締切と参加資格を確認する

```bash
python3 -m bonus_planner check --schedule data/promo_schedule/2026-10.yaml
```

施策ごとの対象ストアと開催日、エントリー締切、運用上の注意が出る。
現在の参加状態で対象外になる施策には印が付く。

---

## 手順3: エントリー日程を提案させる

```bash
python3 -m bonus_planner plan \
    --schedule data/promo_schedule/2026-10.yaml \
    --behavior config/behavior_calibrated.yaml \
    --history data/sales_history_monthly.csv \
    --out out
```

`out/bonus_store_plan_2026-10.{md,csv,json,html}` が出る。

### よく使うオプション

```bash
--budget 300000        # 今月の原資枠を変えて試す
--min-roas 8.0         # 採算ラインを厳しくする
--objective profit     # 売上最大化ではなく利益最大化で解く
--no-sensitivity       # 感応度分析を省略（高速化）
```

## 手順4: 提案をレビューする

機械の提案をそのまま流さない。最低限ここを見る。

1. **「前提の感応度」を先に読む**
   「どの前提でも選ばれる日」はそのまま実行してよい。
   「前提によって採否が変わる日」は実績で反応を確かめる対象。

2. **「前年同月との突き合わせ」を見る**
   ベースライン予測が前年実績とかけ離れていたら、係数かモデルのどちらかが誤っている。
   前年比が0.7〜1.5倍の外なら警告が出る。

3. **「注文下限による目減り」を確認する**
   平均注文単価が5,529円のため、注文下限が5,000円・20,000円・25,000円の施策は
   大きく目減りする（爆買WEEK7%段とモールクーポンは実質機能しない）。

4. **「日別の付与率内訳」で「参加で開く分」を確認する**
   ここがゼロの日は、エントリーしてもモール負担の上乗せが付かず、
   自社のポイントを配るだけ。それでも採用されているなら、
   自社設定率だけで採算が取れると判断されている。

5. **在庫を確認する**
   モデルは在庫を見ていない。推奨日に主力商品の在庫があるか確認する。
   欠品したらポイント原資だけ払って売上が立たない。

6. **エントリー日数の運用負荷**
   日ごとにエントリーする運用が現実的か。多すぎる場合は
   `--min-roas` を上げて絞る。

7. **必ず出たい日がある場合**
   `config/config.yaml` の `mandatory_benefit_ids` に施策IDを書く。
   採算に関わらず先に確保し、残予算で他を最適化する。

## 手順5: 実績を記録してモデルを校正する

### 月次実績（現在の運用）

**ストアクリエイターProの実績エクスポートをそのまま置くだけでよい。**
CP932エンコード・日本語ヘッダーのまま読める。手で転記する必要はない。

`data/sales_history_monthly.csv` として保存する。使う列は次の5つ。

| 列 | 用途 |
|---|---|
| `日付` | `YYYY-MM` |
| `売上合計値` | GMV |
| `注文数 - 注文数合計` | 注文件数 |
| `注文数 - 注文者数合計` | 注文者数 |
| `セッション合計` | 集客と転換率の分離に使う |

> 「前年比」列が何度も現れるため、列名ではなく位置で読んでいる。
> 列の並びが変わった場合は `bonus_planner/calibrate.py` の
> `YAHOO_COLUMNS` を確認すること。

簡易形式（`month,orders,gmv[,days]`）も引き続き使える。

```bash
python3 -m bonus_planner calibrate \
    --history data/sales_history_monthly.csv \
    --schedule data/promo_schedule/2026-10.yaml \
    --today 2026-09-16 \
    --partial-days 14 \
    --out config/behavior_calibrated.yaml
```

**`--schedule` と `--participation` を必ず付けること。**
実績には販促イベントと自社のボーナスストアPlus参加による上振れが
すでに含まれており、これを差し引かないとベースライン予測が過大になる。
補正は集客側（セッション）と転換率側の2系統がある。

### 参加履歴

`data/bsplus_participation.csv` に、参加した日と自社設定率を書く。

```csv
date,store_rate
2026-03-03,0.05
2026-09-11,0.04
```

記録の無い日は非参加として扱う。
**毎月エントリーしたら、その日付をここに追記すること。**
これを怠ると、翌月以降の校正でベースラインが過大になる。

参加履歴の集計と、シェア反応が実測できるかの検証:

```bash
python3 -m bonus_planner participation \
    --history data/sales_history_monthly.csv \
    --participation data/bsplus_participation.csv \
    --today 2026-09-16 --partial-days 14
```

**`--partial-days`**: エクスポートは日数列を持たないため、最終月が当月なら
`--today` から「前日まで」と推定する。実際の期間が違う場合はこれで上書きする。
例: データが9/14までで今日が9/16なら `--partial-days 14`。

`config/store_suggested.yaml` に推奨 `aov` が出る。確認のうえ
`config/config.yaml` に反映する（自動上書きはしない）。

### 日次実績が取れるようになったら

`date,orders,gmv` の形式なら自動で日次モードになり、曜日係数と
給料日サイクル係数も校正できる。

さらに `entered`（ボーナスストアPlus参加の有無）と `bonus_rate` を
記録できれば、市場規模とシェアの弾力性まで校正できる。
これが提案精度に最も効く。

## 校正の精度を上げるコツ

推定の仕組み上、こういうデータが要る。

- **市場規模の弾力性** は「全ストア対象のイベント日」と「平常日」の比較から
- **シェアの反応** は「参加した日」と「参加しなかった日」の比較から

したがって **毎回必ず参加していると、参加の効果が測れない**。
年に数回、影響の小さい日で意図的に参加を見送ると、以降の推定精度が上がる。
この見送りコストは、係数を実測に置き換えられる価値に対して十分安い。

### 月次データでは足りない（日別なら解ける）

参加履歴を揃えても、月次の実績しかないとシェア反応は推定できなかった。
参加開始が成長トレンドの立ち上がりと重なると、両者を分離できないため
（実データでは相関 0.83）。

日別なら、同じ期間の中で参加日と非参加日を直接比較できるのでトレンドの
影響を受けない。実際、日別92日で解けた。

```
python3 tools/analyze_daily.py \
    --daily data/sales_history_daily.csv \
    --participation data/bsplus_participation.csv
```

出力された係数を `config/behavior_priors.yaml` に転記する
（曜日係数・給料日サイクル係数・`market_elasticity`・`intent_elasticity`・
`share_gain_at_reference`）。水準と月次季節係数は月次から校正するので触らない。

ストアクリエイターProの日別実績は**3ヶ月分しか遡れない**。
四半期ごとにエクスポートして貯めておくこと。

### まだ測れていない: `share_elasticity`

自社設定率をほぼ5%固定で運用してきたため、「優位を増やしたときの逓減の強さ」は
測る材料がない。これはプロモーションパッケージですでに優位が付いている日
（プレミアムな日曜日・感謝デー・爆買WEEK）に自社分を上乗せする価値を左右する。

**測り方**: 条件の近い日を選んで自社設定率だけを変える。
たとえば定常施策のみの土曜を +2% と +4% に振り分ける。数日分で足りる。

## パラメータを変えるとき

`config/config.yaml`（自社の経済条件）は実数に合わせて必ず更新する。
特にこの4つは提案結果を大きく動かす。

| 項目 | 確認方法 |
|---|---|
| `promo_package` / `excellent_store` | 参加状態。カレンダーのどの施策が開くかが変わる |
| `gross_margin_rate` | モール手数料・決済手数料・送料・梱包費を引いた後の率 |
| `point_cap_per_order` | ストアクリエイターProのボーナスストア設定画面 |
| `monthly_point_budget` | 販促予算のうちポイント原資に充てる額 |

### 注文明細（注文下限の効き方）

`data/order_values.csv` に金額列（`total_price`）を置く。
ストアクリエイターProの受注明細から `TotalPrice` 列だけ抜き出せばよい。

```bash
python3 -m bonus_planner orders \
    --file data/order_values.csv \
    --schedule data/promo_schedule/2026-10.yaml \
    --profile-out data/order_value_profile.json
```

施策ごとの該当率・実効付与率と、注文下限の「あと一歩」分析が出る。

明細はリポジトリに置かない（`.gitignore`）。代わりに要約統計を
`data/order_value_profile.json` に書き出してコミットする。
これがあれば明細そのものが無くても分布の妥当性をレビューできる。

明細を置くと `config.yaml` の `order_values_file` 経由で自動的に
実効付与率の計算に使われる。無い場合は `aov_sigma` による対数正規近似に
フォールバックするが、SKU価格に張り付いた分布では誤差が大きい。

`config/behavior_priors.yaml`（行動モデル）のうち `base_sessions`・`base_cvr`・`month` は
`calibrate` の出力を使う。手で触るのは弾力性まわりだけ。

## トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| 「推奨できるエントリー日がありません」 | `min_roas` が高すぎるか `gross_margin_rate` が低すぎる。損益分岐の表を確認 |
| 「実績との突き合わせ」で乖離警告が出る | `calibrate` に `--schedule` を付け忘れている可能性が高い。両系統の二重計上補正が効かず予測が過大になる |
| 部分月の水準がおかしい | `--partial-days` で実日数を指定する |
| エントリー日数が多すぎる | `--min-roas` を上げる。感応度の「どの前提でも選ばれる日」だけに絞るのも手 |
| 参加で開く分が全日ゼロ | `eligibility` の書き写しを確認。`bonus_store_plus` を `all` にしていないか |
| 「対象期間外の日付」エラー | 月を跨ぐ施策がある。`extends_to` を設定する |
| 「rate も tiers も coupon_yen もありません」 | 付与内容のない施策。`notes` に移すか値を入れる |
| 原資が想定より桁違いに大きい | `funding` が `store` になっている施策がないか確認 |
