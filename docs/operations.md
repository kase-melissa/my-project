# 月次運用手順

毎月これをなぞれば回る、という手順書。

---

## 月次サイクル

```
前月中旬      販促スケジュールを受領 → YAMLに書き写す
   ↓
前月中旬      check で締切を確認
   ↓
前月中旬      plan でエントリー日程を提案させる
   ↓
前月下旬      提案をレビューして確定 → ストアクリエイターProでエントリー
   ↓
翌月初        実績CSVを更新 → calibrate でモデルを校正
```

---

## 手順1: 販促スケジュールを書き写す

受領した該当月の販促スケジュールを `data/promo_schedule/YYYY-MM.yaml` に書く。
`data/promo_schedule/2026-10.yaml` を雛形としてコピーするのが早い。

書く項目は、イベントごとに:

| 項目 | 内容 |
|---|---|
| `dates` / `period` | 開催日。連続した期間は `period: [開始, 終了]` |
| `entry_required` | エントリーが参加条件か（ほぼ `true`） |
| `entry_unit` | `day`（日ごと）か `period`（期間一括） |
| `entry_deadline` | エントリー締切。省略時は `entry_deadline_days_before` 日前 |
| `traffic_multiplier` | エントリーせずとも得られる集客増 |
| `entry_uplift` | エントリーして初めて得られる上乗せ |
| `min_bonus_rate` | イベント参加に必要な最低還元率 |

**係数がわからないとき**は `calibrate` が出す「イベント別の推定値」をそのまま写す。
初回で実績がないうちは `data/promo_schedule/2026-10.yaml` の値を出発点にし、
毎月実績で更新していく。

### 書き写すときの注意

- 期間一括エントリーのイベントは必ず `entry_unit: period` にする。
  日ごとに抜き差しできる前提で最適化されると、実行不能な提案になる。
- エントリー必須なのに `entry_uplift` を書き忘れると読み込み時にエラーになる。
  「エントリーする価値ゼロ」と評価されるのを防ぐための意図的な仕様。

---

## 手順2: 締切を確認する

```bash
python3 -m bonus_planner check --schedule data/promo_schedule/2026-10.yaml
```

締切順に一覧が出る。締切を過ぎたイベントがあると終了コード1で警告する。

---

## 手順3: エントリー日程を提案させる

```bash
python3 -m bonus_planner plan \
    --schedule data/promo_schedule/2026-10.yaml \
    --behavior config/behavior_calibrated.yaml \
    --out out
```

`out/bonus_store_plan_2026-10.{md,csv,json,html}` が出る。

- `.md` … レビュー用。判断根拠と見送り理由まで書いてある
- `.html` … カレンダー表示。共有用
- `.csv` … 日別データ。Excelで加工する用
- `.json` … 他システム連携用

### よく使うオプション

```bash
# 今月の原資枠を変えて試す
--budget 300000

# 採算ラインを厳しくする
--min-roas 8.0

# 月初にさかのぼって判定したい場合
--today 2026-10-01
```

---

## 手順4: 提案をレビューする

機械の提案をそのまま流さない。最低限ここを見る。

1. **「見送り判断とその理由」を先に読む**
   エントリー必須イベントが「予算上限により見送り」になっていないか。
   なっていれば、原資枠を増やすか他日を削るかの経営判断が要る。

2. **在庫を確認する**
   モデルは在庫を見ていない。推奨日に主力商品の在庫があるか確認する。
   欠品したらポイント原資だけ払って売上が立たない。

3. **高還元率が提案された日**
   `損益分岐の目安` の表と突き合わせる。必要な注文増加率が現実的か。

4. **必ず出たい日がある場合**
   `config/config.yaml` の `mandatory_event_ids` にイベントIDを書く。
   採算に関わらず先に確保し、残予算で他を最適化する。

## 手順5: 実績を記録してモデルを校正する

月が終わったら `data/sales_history.csv` に日次実績を追記する。

```csv
date,orders,gmv,entered,bonus_rate,events
2026-10-25,198,4250000,1,0.04,超PayPay祭|超PayPay祭グランドフィナーレ|5のつく日
```

| 列 | 内容 |
|---|---|
| `date` | 日付 |
| `orders` | 注文件数 |
| `gmv` | 流通総額（円） |
| `entered` | その日ボーナスストアにエントリーしていたか（1/0） |
| `bonus_rate` | エントリー時の還元率（0.04 など） |
| `events` | 販促イベント名。複数は `|` 区切り |

```bash
python3 -m bonus_planner calibrate \
    --history data/sales_history.csv \
    --out config/behavior_calibrated.yaml
```

出力される「イベント別の推定値」を翌月のスケジュールYAMLに反映する。

### 校正の精度を上げるコツ

推定の仕組み上、こういうデータが要る。

- **需要倍率** は「イベント日にエントリーしなかった日」から推定する
- **エントリー上乗せ** は「イベント日にエントリーした日」から推定する

したがって **毎回必ずエントリーしていると、エントリーの効果が測れない**。
同じイベントで片方しかデータがないと「推定不可」と表示される。

年に数回、影響の小さいイベントで意図的にエントリーを見送る月を作ると、
以降の推定精度が上がる。この見送りコストは、係数を実測に置き換えられる
価値に対して十分安い。

## パラメータを変えるとき

`config/config.yaml`（自社の経済条件）は実数に合わせて必ず更新する。
特にこの3つは提案結果を大きく動かす。

| 項目 | 確認方法 |
|---|---|
| `gross_margin_rate` | モール手数料・決済手数料・送料・梱包費を引いた後の率 |
| `point_cap_per_order` | ストアクリエイターProのボーナスストア設定画面 |
| `monthly_point_budget` | 販促予算のうちポイント原資に充てる額 |

`aov_sigma`（注文単価のばらつき）は注文明細から推定する:

```python
from bonus_planner.calibrate import estimate_aov_sigma
print(estimate_aov_sigma([12800, 24800, 9800, ...]))  # 30件以上必要
```

`config/behavior_priors.yaml`（行動モデル）は **手で編集しない**。
`calibrate` の出力を使う。手で触るのは `candidate_rates`（選べる還元率）
と `rate_elasticity` くらい。

## トラブルシューティング

| 症状 | 原因と対処 |
|---|---|
| 「推奨できるエントリー日がありません」 | `min_roas` が高すぎるか `gross_margin_rate` が低すぎる。損益分岐の表を確認 |
| 全部+1%になる | 予算が足りず「広く薄く」に倒れている。`--budget` を上げて比較する |
| エントリー必須イベントが見送られる | 予算制約。`mandatory_event_ids` で確保するか原資枠を増やす |
| `entry_uplift が0です` エラー | エントリー必須イベントに上乗せ係数を書き忘れている |
| 「推定不可」が多い | 対象イベントでエントリー有/無の両方のデータがない（上記コツを参照） |
