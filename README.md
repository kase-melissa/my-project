# ボーナスストア エントリープランナー

Yahoo!ショッピング店の売上最大化のために、**ボーナスストアにエントリーすべき
日程と還元率を、顧客の行動分析にもとづいて利益ベースで提案する** システム。

事前共有される月次の販促スケジュールを入力すると、月次のポイント原資予算の中で
純増効果が最大になるエントリー日程を出力する。見送った日については理由も出す。

---

## 何を解いているか

「プレミアムな日曜日」「Yahoo!ショッピング感謝デー」「超PayPay祭」「爆買いWEEK」など
購入意欲が高まるイベントは、いずれも **エントリーが参加条件** になっている。
全部にエントリーすれば機会損失はゼロになるが、ポイント原資は青天井に増える。

原資は増分売上だけでなく **エントリーしなくても発生したはずの注文にもかかる** ため、
「とりあえず全部入る」は利益を溶かす。逆に絞りすぎると、エントリー必須イベントの
集客をまるごと取り逃がす。

このシステムはその線引きを、日ごとの期待値計算と予算制約下の最適化で行う。

```
純増効果 = 増分GMV × 粗利率 − ポイント原資 + 新規客のLTV
                              ~~~~~~~~~~~~~~
                              全GMVにかかる（自然発生分も含む）
```

## クイックスタート

依存は Python 3.11+ と PyYAML のみ。

```bash
pip install pyyaml

# 1. 販促スケジュールの検証と締切一覧
python3 -m bonus_planner check --schedule data/promo_schedule/2026-10.yaml

# 2. エントリー日程を提案させる
python3 -m bonus_planner plan --schedule data/promo_schedule/2026-10.yaml

# 3. 実績から行動モデルを校正する
python3 -m bonus_planner calibrate \
    --history data/sales_history_sample.csv \
    --out config/behavior_calibrated.yaml

# 4. 校正済みモデルで再提案
python3 -m bonus_planner plan \
    --schedule data/promo_schedule/2026-10.yaml \
    --behavior config/behavior_calibrated.yaml
```

出力（`out/bonus_store_plan_YYYY-MM.*`）:

| 形式 | 用途 |
|---|---|
| `.md` | レビュー用。判断根拠・締切アラート・見送り理由つき |
| `.html` | カレンダー表示。共有用 |
| `.csv` | 日別データ。Excel加工用 |
| `.json` | 他システム連携用 |

## 設計の要点

### エントリー必須イベントの機会損失を明示的に扱う

イベントの効果を2つに分けている。

| 項目 | エントリーしないと |
|---|---|
| `traffic_multiplier` … モール全体の集客増 | **得られる** |
| `entry_uplift` … 特集面掲載＋絞り込み検索での露出＋CVR改善 | **まるごと失う** |

エントリー必須イベントで見送った場合の損失は `entry_uplift` 分そのもので、
これが提案の優先順位を決める。`entry_required: true` かつ `entry_uplift: 0` は
設定ミスとして読み込み時に弾く。

### ポイント上限を効果とコストの両面に反映する

犬猫用家電は単価1〜3万円が中心のため、1注文あたりポイント上限が効く。
注文単価を対数正規分布で近似し、実効還元率を閉形式で計算している。

- コスト面: 実効還元率 < 表示還元率 → 原資は想定より安い
- 効果面: 顧客の体感還元率も頭打ち → 還元率を上げても効果が伸びない

片方だけ見ると判断を誤るので、両方に反映している。

### イベント重複日は掛け算にしない

10/25 のように「日曜 × 5のつく日 × 超PayPay祭グランドフィナーレ」が重なっても、
同じ購買意欲の高い層を取り合うため効果は単純な積にならない。
大きい順に並べて逓減させながら合算する（単純積3.08倍 → 1.90倍）。

### 貪欲法ではなく動的計画法で選ぶ

「見送る or 還元率をひとつ選ぶ」の択一なので multiple-choice knapsack として解く。
費用対効果順に取る貪欲法では「安い日を2つ取るより高い日を1つ取る方が良い」
ケースを取りこぼす。

### 期間一括エントリーを all-or-nothing で扱う

超PayPay祭・爆買いWEEKのように期間通しでしかエントリーできないイベントは、
期間全体で1単位として評価する。日ごとに抜き差しする実行不能な提案を出さない。

## 構成

```
bonus_planner/
  calendar_rules.py  曜日・給料日サイクル・5のつく日・ゾロ目
  behavior.py        需要モデル（乗算モデル・重複逓減・還元率反応）
  economics.py       ポイント原資・実効還元率・損益分岐
  planner.py         エントリー単位の構築と日次見積り
  optimizer.py       予算制約下の最適化（DP）
  calibrate.py       実績からのモデル校正
  report.py          Markdown / CSV / JSON / HTML 出力
  schedule.py        販促スケジュールの読み込みと検証
  cli.py             CLI
config/
  config.yaml              自社の経済条件（粗利率・単価・上限・予算・採算ライン）
  behavior_priors.yaml     行動モデルの初期仮値
data/
  promo_schedule/2026-10.yaml  販促スケジュールの記入例
  sales_history_sample.csv     動作確認用の合成データ
docs/
  model.md           モデル仕様（係数を触る前に読む）
  operations.md      月次運用手順
tools/
  make_sample_history.py  合成データ生成（実データではない）
```

---

## 重要: 係数は必ず自社実績で校正すること

`config/behavior_priors.yaml` の係数は業界的な相場観にもとづく **初期仮値** で、
自社の実測値ではない。そのまま本番判断に使わないこと。

`calibrate` に実績CSVを通すと、曜日・給料日サイクル・季節性・5のつく日の効果を
中央値ベース（外れ値に強い）で推定し、イベント別の推定係数も出力する。

サンプルが足りない項目は仮値のまま残し、レポートとログに明示する。
イベント別推定で「推定不可」と出るのは **サンプル不足** であって、
効果がないという意味ではない。

詳細は [docs/model.md](docs/model.md) と [docs/operations.md](docs/operations.md) を参照。
