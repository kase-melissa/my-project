# ボーナスストア エントリープランナー

Yahoo!ショッピング店の売上最大化のために、**ボーナスストアPlusにエントリーすべき
日程と自社還元率を、販促カレンダーと実績から利益ベースで提案する** システム。

月次の販促カレンダーを入力すると、ポイント原資の予算内で増分GMVが最大になる
エントリー日程を出力する。見送った日については理由も出す。

---

## 何を解いているか

販促カレンダーには毎日7%から14%までの付与率が並んでいる。しかしそのほとんどは
**モール負担**であって、エントリーしてもしなくても顧客に付く。

自社の意思決定は実質2つしかない。

1. **どの日にボーナスストアPlusに参加するか**
2. **自社設定還元率をいくらにするか**

2026年10月の場合、参加によって**モール負担の上乗せが開くのは6日だけ**
（10/2・7・16・20・27・28）。残りの日は参加しても自社のポイントを配るだけになる。
一方その6日は、自社上乗せ0%でも +2% が開くため原資ほぼゼロで注文が伸びる。

この線引きを、日ごとの期待値計算と予算制約下の最適化で行う。

```
純増効果 = 増分GMV × 粗利率 − 増分ポイント原資 + 新規客のLTV
                               ~~~~~~~~~~~~~~~~
                               自社負担ぶんのみ（モール負担は入らない）
```

## クイックスタート

依存は Python 3.11+ と PyYAML のみ。

```bash
pip install pyyaml

# 1. 販促カレンダーの検証と締切一覧
python3 -m bonus_planner check --schedule data/promo_schedule/2026-10.yaml

# 2. 月次実績から行動モデルを校正（--schedule は必須級。理由は後述）
python3 -m bonus_planner calibrate \
    --history data/sales_history_monthly_sample.csv \
    --schedule data/promo_schedule/2026-10.yaml \
    --out config/behavior_calibrated.yaml

# 3. エントリー日程を提案させる
python3 -m bonus_planner plan \
    --schedule data/promo_schedule/2026-10.yaml \
    --behavior config/behavior_calibrated.yaml \
    --history data/sales_history_monthly_sample.csv
```

出力（`out/bonus_store_plan_YYYY-MM.*`）:

| 形式 | 用途 |
|---|---|
| `.md` | レビュー用。前提・感応度・判断根拠・見送り理由つき |
| `.html` | カレンダー表示。共有用 |
| `.csv` | 日別データ。Excel加工用 |
| `.json` | 他システム連携用 |

## 設計の要点

### 1. モール負担と自社負担を分ける

施策ごとに `funding: mall | store` を持たせ、**自社負担ぶんだけをコストに計上する**。
これを混ぜると原資が数倍に膨らみ、提案が成立しない。

2026年10月で自社負担なのは、ストアポイント1% と 自社設定率 だけ。

### 2. 市場規模とシェアを分ける

| 種類 | 効果 |
|---|---|
| **全ストア対象**（5のつく日など） | 競合も同条件。シェアは動かず、モール全体の来訪者が増える |
| **参加資格つき**（ボーナスストアPlus、プロモパッケージ） | 競合に対する優位。シェアが動く |

この2つを1本の反応関数にまとめると、逓減が効きすぎて
**モールが最も集客している5のつく日を避ける**提案になる。実務感覚と逆で、
モデルの作りに起因する歪みである。

シェアは**比率ではなく絶対差**で見る。顧客にとって2ポイント分の価値は、
基準率が7%でも11%でも同じ金額（2万円の注文なら400円）だから。

### 3. 注文下限と付与上限を分布で積分する

高単価商材ではこの2つが逆方向に効く。下限未満の注文には付かず、
上限で頭打ちになる。注文単価を対数正規分布で近似し、閉形式で期待付与率を出す。

実例: モールクーポン1,000円OFF（注文下限25,000円）は、平均単価19,800円では
大半の注文が対象外になり、実効的には約1.2%相当にしかならない。
「1,000円 ÷ 19,800円 = 5%」と数えると大きく誤る。

### 4. コストは限界差分で見る

ストアポイント1%は参加有無に関わらず毎日かかる。エントリー判断で増えるのは差分だけ。
同時に、参加日の原資は**エントリーしなくても発生した注文にもかかる**（カニバリ）。

### 5. 貪欲法ではなく動的計画法で選ぶ

「見送る or 参加して還元率をひとつ選ぶ」の択一なので multiple-choice knapsack
として解く。費用対効果順に取る貪欲法では
「安い日を2つ取るより高い日を1つ取る方が良い」ケースを取りこぼす。

### 6. 期間一括エントリーと月跨ぎを扱う

爆買WEEK（10/30〜11/1）のように期間通しでしかエントリーできない施策は
期間全体で1単位として評価し、日ごとに抜き差しする実行不能な提案を出さない。

### 7. 前提の感応度を必ず出す

付与率への反応は日次データがないと校正できない。そこで弱気・既定・強気の
3シナリオを並べ、**どの前提でも選ばれる日**と**前提によって採否が変わる日**を
分けて示す。前者はそのまま実行でき、後者は実績で確かめる対象になる。

## 重要: 何が実測で何が仮値か

月次実績（`month,orders,gmv`）で校正できるのは限られる。
**できないものは仮値のまま残し、レポート冒頭に明記している。**

| 係数 | 月次実績 | 日次実績 | 日次＋エントリー記録 |
|---|:---:|:---:|:---:|
| `base_orders` | ○ | ○ | ○ |
| 月次季節係数 | △ | ○ | ○ |
| `aov` | ○ | ○ | ○ |
| 曜日係数 | × | ○ | ○ |
| 給料日サイクル係数 | × | ○ | ○ |
| 市場規模・シェアの弾力性 | × | × | ○ |
| `aov_sigma` | × | × | 注文明細が必要 |

△ = 1ヶ月あたり観測1点のため弱い推定（縮小推定で過学習を抑えている）。

**金額の絶対値は目安として扱うこと。** 日ごとの優先順位づけには使えるが、
増分GMVや純増効果の絶対額は実績での検証が必要。

### `calibrate --schedule` を省略しないこと

月次の注文数には販促イベントによる上振れがすでに含まれている。
モデルはそこへさらに市場規模係数を掛けるため、補正しないと
ベースライン予測が系統的に過大になる。`--schedule` を渡すと
その月の市場規模係数の平均で割り、`base_orders` を
「定常施策だけの日の注文数」に引き戻す。

詳細は [docs/model.md](docs/model.md) と [docs/operations.md](docs/operations.md) を参照。
